# 会话回收：为什么改插件，怎么改

[索引](../README.md) · [实现](implementation.md) · [验证](validation.md)

这份文档回答两件事：**为什么这个问题该由 tio 插件改，而不是宿主改**，以及**具体怎么改**。

---

## 1. 结论

1. **现象要拆成两件事。** Argus 列表里残留一行 tio.exe 并弹「没有权限结束」——这是 Argus 自己的缺陷（它握着进程句柄，正常退出的进程也会残留；`TerminateProcess` 对已死进程返回 `ERROR_ACCESS_DENIED(5)`，它把这当成权限问题），**我们改不了，也不该拿它当验收标准**。
2. **我们能改、也必须改的是另一件事**：插件被强杀时，wt 里的会话 tio.exe 活了下来，继续占着 COM 口，导致下一次会话开不了串口。
3. **改动落在插件侧**，因为只有插件知道自己的会话进程是谁、跑在哪、该怎么停。宿主侧另有两处契约洞（shutdown 漏发给启动中的插件、拿到回答就关作业不等进程真退出），那是第二批的宿主改动，与本文档并行推进。
4. **不依赖宿主改任何协议**：stop 文件写在插件自己的 dataDir 里，与 `tio.json` 同级。

---

## 2. 现象

用户看到的：

```
Argus 进程列表：tio 串口终端 · Win顺 插件 / tio.exe  PID 85536
红色提示：没有权限结束 tio 串口终端 · Win顺 插件。可以在设置中启用特权服务，或以管理员身份运行 Argus；……
```

「以管理员身份运行」这条建议是错的，但**给出的方向是对的**：这个进程确实已经结束了，只是 Argus 还握着它的句柄，所以进程表里留着这一行，而 Argus 对已结束进程调用 `TerminateProcess` 拿到的是 `ERROR_ACCESS_DENIED(5)`，被它当成了权限不足。用户实测：重启 Argus 后这一行消失。

所以这一行本身不是我们的问题。**我们的问题是它背后那件事**：

- 宿主退出 / 插件被停用 / 插件崩溃时，插件来不及把会话收干净就被强杀；
- wt 后端下，会话 tio.exe 是常驻 `WindowsTerminal.exe` 的孩子，**不在我们的作业对象里**，所以作业兜底对它无效；
- 这个 tio.exe 继续开着 COM 口。用户下一次启动 tio，端口被占，失败。

---

## 3. 证据

| 事实 | 证据 | 状态 |
|---|---|---|
| wt 后端的会话 tio.exe 的父进程是常驻 `WindowsTerminal.exe`，不是插件 | `native.h:884` `findWtChild()` 的实现：扫进程表，取 `tio.exe` 且父进程名是 `windowsterminal.exe` 且创建时间 ≥ 启动时刻，必须唯一命中 | 代码可查 |
| 因此它不在我们的作业里，「Job 兜底，无 orphan」在 wt 后端为假 | `plugin-design.md` 里那句承诺只在 conhost 后端成立 | **文档承诺与实现不符** |
| conhost 后端的会话是插件直接 `CreateProcessW` 起的，是插件的子进程，继承作业 | `native.h:999`；`native.h:1009` 走 conhost 分支时直接用拿到的 PID | 代码可查 |
| 插件的清理预算可能超过宿主给的 2 秒 | `controller.h:429`：串行停每个会话，每个最多 1200 ms；2 个会话 = 2.4 s。宿主 `Host.cpp:38` `kShutdownGraceMs = 2000` | 代码可查 |
| SDK 写明的契约是「回答前清理完，宿主等约 2 秒」 | `winshun.h:957-961` 的 `shuttingDown()` 注释 | 代码可查 |
| 插件被强杀后没有任何可回收的痕迹 | `native.h:962` 只有一句注释「dataDir: logs and the stop file live here」，全仓库没有 stop file 的实现 | 代码可查 |
| Argus 的残留行会随 Argus 重启消失 | 用户实测 | **实测** |

## 4. 为什么责任在插件

原则：**外部性 ≠ 责任外部性**。

| 进程 | 谁拉起来的 | 谁该负责它消失 |
|---|---|---|
| `WindowsTerminal.exe` | 微软的常驻程序，插件只是通过 `wt.exe` 请它开窗 | **谁都不该关它**，它是用户的终端 |
| 会话 `tio.exe`（wt 后端） | **我们的插件**（`logic.h:371` `planLaunch` 拼出 `wt.exe … -- tio.exe …`） | **插件**。它跑在别人家的终端里，但它是我们请来的 |
| 会话 `tio.exe`（conhost 后端） | 我们的插件 | 插件，且已在作业内，插件死它跟着死 |

按「谁掌握解决它所需的信息」分工：

| 问题 | 归谁 | 理由 |
|---|---|---|
| 插件被杀后如何找回自己的会话进程 | **插件** | 只有插件知道会话的 COM 号、token、pid、创建时间 |
| 崩溃后的补救机制（stop 文件 + 启动回收） | **插件** | 全在插件自己的 dataDir 内自足完成，宿主无需改协议 |
| 清理时间超过 2 秒预算 | **插件** | 2 秒是 SDK 写明的契约（`winshun.h:957`），超预算的一方是插件 |
| shutdown 漏发给启动中的插件 | 宿主 | 只有宿主知道插件处于哪个阶段 |
| 拿到回答就关作业、不确认进程真退出 | 宿主 | 只有宿主知道作业与 runner 的生命周期 |

**宿主那两处不在本文档范围**，另文处理。但要说明一点：即使宿主那两处都修好，插件被强杀的场景依然存在（宿主崩溃、作业被杀、机器重启），所以插件侧的回收机制不是「宿主会照顾我」的补丁，它必须独立成立。

---

## 5. 怎么改

### 5.1 P1：stop 文件 + 启动时回收

**目标**：插件被强杀（来不及清理）后，会话进程不会长期霸占 COM 口；下一次插件启动时把它收回来。

**落点**：`dataDir\sessions\<sessionId>.json`，与 `tio.json` 同级（`controller.h:654` `settingsPathLocked()` 就是 `dataDir\tio.json`）。dataDir 由宿主在 `initialize` 时给出，插件已经在往里写 `tio.json`，不需要新权限（`normal` 沙箱下 `files:write` 只是声明，见宿主 `docs/plugins.md:416`）。

**文件内容**：

```json
{
  "v": 1,
  "ownerPid": 1234,
  "ownerCreated": 123456789,
  "sessionId": "s-3f9a21c",
  "com": 8,
  "device": "/dev/ttyS7",
  "backend": "wt",
  "pid": 85536,
  "created": 131000000000000000,
  "launchedAt": 1730000000000
}
```

- `ownerPid` + `ownerCreated`：**这是归属判定的关键**。回收时如果 owner 的 pid 还活着且创建时间对得上，说明另一个插件实例正在管这个会话，**跳过不动**（防止两个 Win顺 实例互相杀对方的会话）。
- `pid` + `created`：会话进程的进程号与创建时间。创建时间用来防 PID 复用——现有 `stopOwned()`（`native.h:923`）已经在比对它，回收逻辑复用同一套判定。
- `sessionId`：会话 token（`controller.h:641` `newToken()`），同时也是 wt 窗口标题里的那串（`logic.h:403`），用来在「pending」状态下认领进程。
- `pid` 为 0 表示**这次启动还没拿到 PID**（wt 后端要等 `wt.exe` 把进程交给常驻终端，见 `native.h:1020-1025`），进程号是之后才补上的。

**生命周期**：

| 时机 | 动作 |
|---|---|
| 启动会话**之前** | 写 `pending` 文件（`pid=0`，带 `sessionId`、`com`、`launchedAt`）——否则「进程起来了、文件还没写」这一瞬被打死，就再也认不出来了 |
| 启动成功后 | 重写文件，补上 `pid` + `created`（临时文件 + `MoveFileEx` 原子替换，避免写一半被打死留下坏文件） |
| 会话正常停止 | 删文件 |
| 插件启动时 | 扫描 `dataDir\sessions\`，逐个处理（见下） |

**回收算法**（插件启动时，在 `initialized()` 里、拿到 dataDir 之后立刻做）：

```
对 sessions\ 下每个文件：
  1. 解析；解析失败 → 记一条诊断，删文件（坏文件留着只会一直报错）
  2. owner 还活着（pid 在 + 创建时间对得上） → 跳过（另一个实例在管）
  3. pid != 0：
       pid 还在 且 创建时间对得上 → 是我们的 → stopOwned(pid, created, 800)
       pid 不在了                        → 进程自己没了 → 直接删文件
       pid 在但创建时间对不上             → PID 被复用，不是我们的 → 删文件，不动它
  4. pid == 0（pending）：
       扫进程表找 tio.exe 且父进程是 windowsterminal.exe 且创建时间 ≥ launchedAt
       → 读它的命令行，取末尾的设备参数（/dev/ttyS(n-1)）→ 映射回 COM n+1
       → COM 与本文件的 com 一致 → 认领 → 停掉
       （命令行读不出来或多于一个命中 → 不猜，保留文件，下次再来）
  5. 停成功 → 删文件
```

第 4 步需要一个新的 native helper：读别的进程的命令行（`NtQueryInformationProcess` + `ProcessCommandLine = 60`）。这是本方案唯一的新增 Win32 能力，约 60 行。**为什么必须读命令行**：wt 后端下多个会话的 tio.exe 是同一个 `WindowsTerminal.exe` 的孩子，光靠父进程和创建时间无法区分是哪个会话的；tio 的命令行末尾带着设备路径（`logic.h:355` `tioArguments` 的最后一个参数），它唯一地指向 COM 号。

**预算**：回收发生在插件启动时，不占 shutdown 的 2 秒窗口。每会话 800 ms 优雅 + 400 ms 兜底，总量上限 4 s；超时的会话**保留文件不删**，下一个插件实例再来一次（宁可多收一次，也不能把文件删了却没停干净）。

### 5.2 P2：并行停会话，总预算 ≤ 1.2 s

**现状**（`controller.h:429`）：

```cpp
for (const auto& [pid, created] : victims)
    if (pid != 0)
        stopOwned(pid, created, hostShutdown ? 1200 : 2000);
```

串行。每个会话最多 1200 ms 优雅期，之后还有最多 1500 ms 的强杀等待（`native.h:953-954`）。两个会话就可能吃掉 2.4 s，超过宿主的 2 s。

**目标**：

- 所有受害会话**并行**停止：每个会话一个线程，各自 `stopOwned(pid, created, 800)`；
- 控制器等所有线程，总预算 ≤ **1200 ms**；
- 预算耗尽还没退的，直接 `TerminateProcess` 强杀，不再等；
- 会话状态**按真实结果**标记：现在无论停成功与否都 `markExited`（`controller.h:437`），改完后要区分「优雅退出 / 强杀 / 已经不在了」，并写进诊断视图。

**预算的推导**：

| 项 | 值 | 依据 |
|---|---|---|
| 宿主给的窗口 | 2000 ms | `Host.cpp:38` `kShutdownGraceMs = 2000`；SDK 注释 `winshun.h:957` 也写「约 2 秒」 |
| 写回答 + 进程退出 | 100 ms | 一次 stdout 写加进程退出的实测量级（估算） |
| 余量 | 200 ms | 留给人机交互与调度抖动 |
| **插件可用预算** | **1700 ms → 取 1200 ms** | 留 500 ms 额外余量，避免踩线被杀 |

**语义不能变**：一个 COM 号同时只有一个会话；停止后端口立即可再打开；会话标记为已退之前，进程必须真的没了（否则界面说停了、端口还占着，比现在更糟）。

### 5.3 明确不做

- **不改宿主协议，不加宿主接口**：stop 文件与回收完全在插件内部闭环。
- **不新增 manifest 权限**：只写自己的 dataDir，`normal` 沙箱下不需要 `files:write`。
- **不依赖嵌套作业对象**：理论上插件可以自建作业把会话 tio.exe 收编进去，插件一死内核就带走孩子（`native.h:923` 注释里那句「stop file」的另一种解法）。这条受嵌套作业规则限制，且 Windows Terminal 是否已经给自己的子进程套了作业**未实测**，所以不作为方案主体，放进第 8 节待实测项。
- **不动 Argus**：它的残留行与红色提示是它自己的缺陷。

## 6. 验收

**能当验收标准的**（对应 [TEST-PLAN.md](../TEST-PLAN.md) 新增用例）：

| 编号 | 场景 | 断言 |
|---|---|---|
| T-T16 | 插件被强杀（模拟：直接 `TerminateProcess` 插件进程） | 会话 tio.exe 仍在（wt 后端），但 COM 口被它占着 |
| T-T17 | 强杀后重新启动插件 | 启动时回收动作发生：孤儿 tio.exe 被停掉，`sessions\` 目录清空，COM 口立即可再打开 |
| T-T18 | 两个插件实例同时在跑 | 后启动的那个**不**回收前一个的会话（owner 存活则跳过） |
| T-T19 | PID 被复用 | stop 文件里的 pid 指向别的进程时，不动它，只删文件 |
| T-T20 | 两个会话 + 宿主 shutdown | 插件在 2 秒内完成清理并给出回答（当前实现会超） |

**不能当验收标准的**：

- ❌ 「Argus 不再显示 tio.exe」——只要 Argus 握着句柄，正常退出的进程也会在它列表里残留。这一项我们无法通过任何改动达成。
- ✅ 换成：「宿主退出后，COM 口立刻可被下一次会话打开」。

## 7. 代价与残留

| 项 | 估计 | 依据 |
|---|---|---|
| 新增代码 | ≈ 250 行 | 读进程命令行 ≈ 60 行；stop 文件读写与回收 ≈ 120 行；并行停止 ≈ 40 行；其余为接线 |
| 新增断言 | ≈ 20 条 | 回收逻辑的纯逻辑部分可进 L0（`tio_tests.exe`），真实进程部分进 L1/L2 |
| 需要新增的测试层 | 无 | 复用现有 L0 / L1 / L2+ / L3 |
| 回归风险点 | 并行停止 | 端口复用的时序断言（`integration.py --launch` 里已有「停后 COM8 立刻可再打开」） |

**残留风险**：

1. **孤儿窗口期**：插件被杀到下一次插件启动之间，wt 里的 tio.exe 仍占着 COM（这段时间用户手动起 tio 会失败）。彻底消掉需要第 8 节的嵌套作业方案。
2. **pending 状态的认领可能失败**：命令行读不出来时宁可留着文件下次再收，也不猜——代价是多占一个窗口期。
3. **多 Win顺 实例**：owner 存活即跳过的规则能防住互杀，但如果前一个实例是被强杀的（owner 已死），后一个实例会回收它的会话——这正是我们要的行为。
4. **回收时机**：只在下一次插件启动时回收。插件 `start` 是 `lazy`（`plugin.json:27`），用户不打开 tio 就不会触发。**所以启动时的回收不能挂在插件启动上，要挂在宿主可触发的路径上**——这一点在实现前需要确认宿主是否提供「插件被唤醒」的通知，否则只能靠 dataDir 里有 stop 文件时在 `query` 里触发回收。

## 8. 待实测项

| 项 | 为什么重要 | 怎么测 |
|---|---|---|
| Windows Terminal 是否给自己的子进程套了作业对象 | 决定「插件自建作业收编会话进程」这条路走不走得通 | 启动一次 wt 会话，用 `QueryInformationJobObject` 或 Process Explorer 查 tio.exe 的 Job 归属 |
| 嵌套作业是否被允许 | 同上；Win8+ 支持嵌套，但受父作业的 breakaway 标志限制 | 插件自建 `KILL_ON_JOB_CLOSE` 作业，把会话 tio.exe `AssignProcessToJobObject` 进去，看是否 `ERROR_ACCESS_DENIED` |
| 强杀插件后，wt 会话的实际存活时间 | 量出第 7 节的「孤儿窗口期」到底有多长 | 强杀插件后轮询 tio.exe 是否还在 |
| 读别的进程命令行在本机是否可用 | 回收算法的第 4 步依赖它 | 写个探针读一次自己或别人的命令行 |

以上四项未实测之前，本文档的 P1 走的是**不依赖嵌套作业**的路径（用户态 stop 文件），实测结果可能让第 5.3 节的「明确不做」变成「可做」。
